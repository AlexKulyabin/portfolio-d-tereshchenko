## 1. Что делаем

Сайт-визитка эксперта в области охраны труда и пищевой безопасности с тремя посадочными
страницами под платный трафик (Яндекс.Директ / РСЯ) и админ-панелью для самостоятельного
редактирования текстов, цен и изображений.

Три услуги:

1. **Оценка профессиональных рисков** (ОПР)
2. **Нормирование труда**
3. **Разработка системы ХАССП** (HACCP)

Ключевые требования из ТЗ:

| Требование | Как закрываем |
| --- | --- |
| Отдельная страница на каждую услугу | 3 посадочные страницы с единым каркасом, разным контентом и SEO |
| Услуги в шапке и подвале | Меню в header + колонка «Услуги» в footer, на всех страницах |
| Реклама в Директе / РСЯ | Разметка целей, UTM, микроразметка, юридические страницы для модерации |
| Яндекс.Метрика | Счётчик с отложенной загрузкой, вебвизор, 5 целей |
| Самостоятельное редактирование текста и картинок | Админка на `/admin` с авторизацией, черновик → публикация |
| Цены: 3 пакета на услугу | Блок тарифов, редактируется в админке (можно добавлять/удалять строки) |
| Об эксперте | Отдельный блок на каждой странице + расширенный блок на главной |
| Срок от 3 к. д., выезд от 1 к. д. | Блок «Сроки» на каждой странице услуги, значения редактируемые |
| Синие градиенты, строгий стиль | Дизайн-система на тёмно-синем / синем / белом (раздел 5) |
| Загрузка 3–5 с | Целимся жёстче: LCP < 1,5 с на 4G (раздел 10) |
| Форма обратной связи | Форма с телефоном/почтой, уведомления в Telegram и на e-mail |
| Контакты сверху и снизу | Телефон + мессенджеры в шапке, полный блок в подвале |

## 2. Технологический стек и почему именно он

**Рекомендуемый вариант:**

| Слой | Решение |
| --- | --- |
| Сборка | Vite 6 |
| UI | React 19 + TypeScript |
| Стили | Tailwind CSS v4 (CSS-first конфиг, без `tailwind.config.js`) |
| Роутинг | React Router 7 |
| Пререндер | `vite-react-ssg` — на выходе готовые HTML-файлы для каждой страницы |
| Формы | React Hook Form + Zod |
| Хостинг | Firebase Hosting (CDN, бесплатный SSL, свой домен) |
| БД | Cloud Firestore |
| Авторизация админки | Firebase Authentication (e-mail + пароль) |
| Изображения | Firebase Storage + конвертация в WebP на клиенте перед загрузкой |
| Приём заявок | Отдельная функция (см. раздел 8 — есть нюанс по 152-ФЗ) |

**Почему не Next.js.** Next.js на Firebase App Hosting дал бы SSR «из коробки», но
тянет за собой Cloud Run: холодные старты, обязательный тарифный план Blaze с оплатой
за запросы, заметно более сложный деплой и отладка. Для сайта из 6 страниц это лишнее.
Пререндеренная статика на CDN даёт TTFB порядка 30 мс и стоит ноль — при том же качестве
SEO. Если через год потребуется блог на сотни статей, переезд на Next.js возможен без
переписывания компонентов.

**Почему не голый SPA.** Чистый SPA отдаёт роботам пустой `<div id="root">`. Яндекс
исполняет JavaScript, но индексирует такие страницы медленнее и хуже, а для платного
трафика важна ещё и скорость первой отрисовки. `vite-react-ssg` решает это одной
строчкой в конфиге: на выходе те же React-компоненты, но собранные в готовый HTML.

## 3. Архитектура контента: как связаны админка, база и статика

Главный компромисс проекта: статика быстрая и хорошо индексируется, но контент должен
меняться из админки без участия разработчика. Решается в два уровня.

**Уровень 1 — снапшот на сборке.** Перед `vite build` скрипт `scripts/fetch-content.mjs`
забирает опубликованный контент из Firestore и кладёт в `src/content/snapshot.json`.
Пререндер запекает эти тексты и цены прямо в HTML. Робот и первый экран пользователя
получают актуальный контент мгновенно, без единого запроса к базе.

**Уровень 2 — обновление в рантайме.** После гидратации страница одним `fetch`
подтягивает `content.json` (около 30 КБ gzip, отдаётся с CDN) и, если версия новее
запечённой, обновляет тексты. То есть правка в админке видна на сайте сразу — просто
до следующей пересборки её видит браузер, а не поисковый робот.

**Уровень 3 (фаза 2, опционально) — автопересборка.** Кнопка «Опубликовать» в админке
дёргает Cloud Function, та шлёт `repository_dispatch` в GitHub Actions, экшен
пересобирает и деплоит сайт. Через 2–3 минуты обновлённый контент есть и в HTML.
Пока этого нет, пересборка запускается вручную одной командой.

Практический смысл: заказчик правит цену — она меняется на сайте сразу; поисковики
подхватывают её при следующей пересборке. Для сайта, где контент меняется раз в месяц,
этого достаточно.

## 4. Карта сайта и структура страниц

### Маршруты

```
/                                        Главная
/otsenka-professionalnyh-riskov          Оценка профрисков
/normirovanie-truda                      Нормирование труда
/razrabotka-hassp                        Разработка системы ХАССП
/kontakty                                Контакты
/politika-konfidencialnosti              Политика обработки персональных данных
/soglasie-na-obrabotku-dannyh            Согласие на обработку ПД
/admin                                   Админка (закрыта авторизацией, не индексируется)
*                                        404
```

Слаги — транслитом: Яндекс учитывает вхождение ключевого слова в URL, и такие адреса
понятнее в отчётах Метрики.

### Главная

1. **Первый экран** — тёмно-синий градиент, заголовок с позиционированием
   («Охрана труда, нормирование и ХАССП под ключ»), подзаголовок с географией
   («выезд по России»), две кнопки: «Получить расчёт» и «Позвонить».
2. **Три услуги** — карточки-ссылки с иконкой, коротким описанием и ценой «от».
3. **Об эксперте** — фото, опыт, образование, сертификаты, членство в СРО (если есть),
   цифры: лет в профессии, выполненных проектов, отраслей.
4. **Почему обращаются** — 4–6 тезисов: сроки, выезд, документы «под ключ», сопровождение
   проверок, договор, гарантия доработок.
5. **Как проходит работа** — 4 шага с указанием сроков (заявка → аудит → документы → сдача).
6. **Отрасли / кейсы** — где работал: производство, общепит, торговля, логистика.
7. **Отзывы** — текст, компания, должность (при наличии).
8. **FAQ** — 6–8 вопросов с микроразметкой `FAQPage`.
9. **Форма заявки** + контакты.

### Страница услуги (единый каркас, разное наполнение)

1. **Первый экран** — название услуги, для кого, срок и цена «от», кнопка.
2. **Зачем это нужно** — требование закона + риск штрафа. Здесь важна конкретика:
   - *Оценка профрисков* — ст. 209, 214, 218 ТК РФ; приказ Минтруда № 776н от 28.12.2021;
     ответственность по ст. 5.27.1 КоАП РФ.
   - *Нормирование труда* — ст. 159–163 ТК РФ; постановление Правительства РФ № 804
     от 11.11.2002; методические рекомендации Минтруда.
   - *ХАССП* — ст. 10 ТР ТС 021/2011 (обязательность процедур на принципах ХАССП);
     ГОСТ Р 51705.1-2001; ISO 22000; ответственность по ст. 14.43 КоАП РФ.
3. **Что входит в работу** — перечень с описанием результата.
4. **Что получите на руки** — список документов (реестр опасностей, карты оценки рисков,
   план мероприятий; нормы времени и численности; программа производственного контроля,
   блок-схемы, рабочие листы ХАССП и т. д.).
5. **Тарифы** — 3 пакета: «Базовый» / «Стандарт» / «Под ключ». Для каждого: цена,
   что входит, срок, кнопка. Средний пакет визуально выделен как рекомендованный.
6. **Сроки** — «разработка от 3 календарных дней», «выезд по России от 1 календарного дня».
7. **Об эксперте** — компактная версия блока с главной.
8. **FAQ по услуге** — 4–6 вопросов.
9. **Форма** — с предвыбранной услугой.

> Тексты по услугам можно сгенерировать (это допускает ТЗ), но нормативные ссылки,
> сроки и состав документов **обязательно должен вычитать заказчик** перед публикацией:
> в этой сфере ошибка в номере приказа бьёт по экспертности сильнее, чем плохой дизайн.

### Дополнительно (рекомендую, не входит в обязательный объём)

- **Калькулятор стоимости** — 3–4 вопроса (услуга, число рабочих мест / сотрудников,
  регион, срочность) → вилка цены и предзаполненная форма. Сильно поднимает конверсию
  холодного трафика с РСЯ.
- **Лид-магнит** — «Чек-лист: что проверяет ГИТ» в PDF в обмен на контакт.

## 5. Дизайн-система

Направленность заказчика — B2B-консалтинг в сфере, где продают компетентность и снижение
юридического риска. Значит: сдержанность, читаемость, доказательства. Никакой «креативной»
графики, стоковых рукопожатий и анимаций ради анимаций.

### Палитра

```
--navy-950  #071633   фон первого экрана, подвал
--navy-900  #0B2545   тёмные секции
--blue-700  #1D4ED8   основной акцент, кнопки
--blue-600  #2563EB   градиент, ховеры
--sky-400   #38BDF8   тонкие акценты, иконки на тёмном
--slate-900 #0F172A   основной текст
--slate-600 #475569   вторичный текст
--slate-200 #E2E8F0   границы
--white     #FFFFFF   фон контента
```

Градиенты — только как фон крупных секций (`navy-950 → blue-700`, диагональ 135°) и
как тонкая заливка карточек тарифов. Текст градиентом не заливаем: страдает читаемость
и антиалиасинг.

### Типографика

- Заголовки — **Manrope**, начертания 600/700.
- Текст — **Inter** (или **Golos Text**, если нужен более «отечественный» характер).
- Шрифты self-hosted: подмножество с кириллицей, формат woff2, `font-display: swap`,
  `<link rel="preload">` на основное начертание. Google Fonts не подключаем — это
  и внешняя зависимость, и лишние 200–400 мс, и вопросы к доступности из РФ.
- Шкала: 14 / 16 / 18 / 20 / 24 / 32 / 40 / 56. Основной текст — 18 px, высота строки 1,7.

### Приёмы оформления

- Крупная типографика и много воздуха вместо декора; секции по 96–128 px по вертикали.
- Тонкие границы `1px slate-200` и мягкие тени вместо тяжёлых карточек.
- Bento-сетка для блока «Почему обращаются» и «Что входит».
- Иконки — один набор в линейном стиле (Lucide), единая толщина штриха.
- Появление блоков при скролле — короткое (200–250 мс), только opacity + сдвиг на 8 px.
  Реализуем на CSS (`IntersectionObserver` + класс), без анимационных библиотек в бандле.
- Обязательно `prefers-reduced-motion: reduce` — полностью отключает анимации.
- На мобильных — липкая нижняя панель с кнопками «Позвонить» и «Написать в WhatsApp».
- Контраст текста не ниже AA (4,5:1); фокус-кольца видимые; вся навигация с клавиатуры.

### Компоненты (`src/components/ui`)

`Button`, `Section`, `Container`, `Heading`, `Card`, `PricingCard`, `Accordion`,
`Badge`, `Stat`, `Input`, `Select`, `Checkbox`, `FormField`, `Modal`, `Breadcrumbs`.

## 6. Модель данных (Firestore)

```
settings/site
  phone, phoneRaw, email, telegram, whatsapp, address, workHours
  legal: { name, inn, ogrnip, type }        // для Директа и оферты
  metrikaId, yandexVerification
  socials: [...]

pages/home
  hero: { title, subtitle, ctaPrimary, ctaSecondary, image }
  about: { name, role, photo, bio, credentials[], stats[] }
  advantages: [{ icon, title, text }]
  steps: [{ number, title, text, duration }]
  industries: [...]
  testimonials: [{ text, author, company, position }]
  faq: [{ q, a }]
  seo: { title, description, ogImage }

services/{slug}            // otsenka-professionalnyh-riskov | normirovanie-truda | razrabotka-hassp
  order, title, shortTitle, slug, icon, summary
  hero: { title, subtitle, image }
  why: { title, body, legalRefs[] }
  included: [{ title, text }]
  deliverables: [...]
  packages: [{ name, price, priceNote, features[], duration, highlighted }]
  terms: { development, visit }             // «от 3 календарных дней», «от 1 календарного дня»
  faq: [{ q, a }]
  seo: { title, description, ogImage }

published/current          // готовый объединённый JSON — то, что читает сайт
  version, publishedAt, data

leads/{id}                 // см. раздел 8 — возможно, вынесем из Firestore
media/{id}                 // путь в Storage, размеры, alt
```

Каждая сущность описана Zod-схемой в `src/schemas/`. Из этих же схем автоматически
строятся формы админки — это экономит время и гарантирует, что структура данных и
редактор не разъедутся.

Черновик и публикация: админка пишет в `pages/*` и `services/*` (черновик), кнопка
«Опубликовать» собирает всё в `published/current` и в `content.json` в Storage.
Предпросмотр черновика — `/?preview=1`.

## 7. Админка

**Доступ.** `/admin` → Firebase Auth (e-mail + пароль, аккаунт создаётся вручную).
Правила Firestore: чтение `published/current` — всем, всё остальное — только
авторизованным с custom claim `admin: true`. Правила Storage — по той же логике.
Страница закрыта от индексации (`noindex` + `robots.txt`).

**Разделы:**

| Раздел | Что редактируется |
| --- | --- |
| Главная | Все блоки главной, включая повторяемые списки (преимущества, шаги, отзывы, FAQ) |
| Услуги | Три страницы услуг: тексты, состав работ, тарифы, сроки, FAQ, SEO |
| Контакты и реквизиты | Телефон, почта, мессенджеры, юр. данные, ID Метрики |
| Заявки | Список обращений с фильтрами и выгрузкой в CSV |
| Медиа | Загруженные изображения, замена, alt-тексты |

**Редактор.** Поля с валидацией, для длинных текстов — простой rich-text (TipTap:
жирный, курсив, списки, ссылки — без произвольного HTML). Повторяемые блоки можно
добавлять, удалять и перетаскивать. Загрузка изображений: drag-and-drop, автоматическое
сжатие и конвертация в WebP прямо в браузере (`browser-image-compression` + canvas),
ограничение по размеру, обязательный alt.

**Важно для скорости публичного сайта:** весь код админки и Firebase SDK грузятся
отдельным чанком по ленивому маршруту. Публичные страницы не тянут Firebase SDK
вообще — они читают один статический `content.json`. Это экономит около 150 КБ.

**Защита от ошибок.** Черновик, предпросмотр, подтверждение публикации, история
последних 10 версий с возможностью откатиться.

## 8. Формы, заявки и 152-ФЗ

### Форма

Поля: имя, телефон (с маской), e-mail, услуга (селект, предзаполняется на странице
услуги), комментарий, чекбокс согласия на обработку персональных данных со ссылкой
на политику. Валидация на лету, понятные ошибки, состояние отправки, экран «спасибо».

Антиспам: honeypot-поле + проверка времени заполнения + ограничение частоты отправок.
Если пойдёт спам — подключаем Yandex SmartCaptcha (в РФ надёжнее reCAPTCHA).

Уведомления: Telegram-бот (мгновенно, бесплатно, удобно с телефона) + дубль на e-mail.

### Юридический нюанс, который надо решить до старта

Часть 5 статьи 18 152-ФЗ требует, чтобы запись, систематизация и хранение персональных
данных граждан РФ велись в базах, расположенных на территории России. Firestore
находится за пределами РФ. Сайт-визитка на Firebase — обычная практика, но приём и
хранение заявок в Firestore формально этому требованию не соответствует. Два варианта:

- **Вариант А (просто).** Заявки идут в Firestore + Telegram. Быстро, дёшево,
  но остаётся регуляторный риск. Так работает множество сайтов.
- **Вариант Б (рекомендую).** Статика остаётся на Firebase, а форма отправляется
  в Yandex Cloud Function (регион РФ), которая шлёт заявку в Telegram и на
  Яндекс.Почту и при необходимости пишет в YDB. Персональные данные не покидают РФ.
  Дополнительно: +4–6 часов работы, около 0 ₽ в месяц при таком трафике.

В обоих вариантах нужны: политика обработки ПД, отдельная страница согласия,
чекбокс в форме и уведомление в Роскомнадзор об обработке ПД (подаётся через
портал РКН, бесплатно). Без политики конфиденциальности объявления в Директе
не пройдут модерацию.

Cloud Functions (в варианте А) требуют тарифного плана Blaze — то есть привязанной
карты. При таком трафике фактические расходы близки к нулю, но карта нужна.
Вариант Б от Blaze не зависит.

## 9. SEO, Метрика и подготовка к Директу

**SEO-база**

- Уникальные `title` / `description` на каждой странице, редактируются в админке.
- Один `h1` на страницу, корректная иерархия заголовков.
- Микроразметка Schema.org: `ProfessionalService` (организация), `Service` (каждая
  услуга с `offers` по тарифам), `FAQPage`, `BreadcrumbList`.
- Open Graph и Twitter Card, генерируемая `og:image` под каждую услугу.
- `sitemap.xml` и `robots.txt` генерируются на сборке.
- Канонические URL, редирект `www` → без `www`, HTTPS-редирект.
- Подтверждение прав в Яндекс.Вебмастере (мета-тег) и Google Search Console.

**Яндекс.Метрика**

- Счётчик с вебвизором, картой скроллинга и точным показателем отказов.
- Загрузка отложенная (`requestIdleCallback` или первое взаимодействие), чтобы
  не портить LCP.
- SPA-переходы: `ym(ID, 'hit', url)` на каждую смену маршрута — иначе Метрика
  посчитает весь визит одной страницей.
- Цели: `form_submit`, `click_phone`, `click_email`, `click_whatsapp`,
  `click_telegram`, `calculator_complete` (если делаем калькулятор).
- Электронная коммерция не нужна, но цели должны быть настроены до запуска рекламы,
  иначе Директ не сможет обучать автостратегии.

**Под Директ / РСЯ**

- Разные посадочные под разные группы объявлений — уже заложено структурой сайта.
- Поддержка UTM-меток и `yclid` (сохраняем в скрытые поля формы, чтобы видеть,
  с какого объявления пришла заявка).
- На странице должны быть: юридическое наименование или ИНН, контактный телефон,
  политика конфиденциальности — модерация проверяет.
- Мобильная версия — приоритет: с РСЯ приходит преимущественно мобильный трафик.

## 10. Производительность

Целевые показатели (мобильный, 4G, Lighthouse):

| Метрика | Цель |
| --- | --- |
| LCP | < 1,5 с |
| CLS | < 0,05 |
| INP | < 200 мс |
| JS публичной страницы | < 120 КБ gzip |
| Lighthouse Performance | 95+ |

ТЗ допускает 3–5 секунд, но для платного трафика каждая лишняя секунда — это
потерянные деньги, поэтому целимся заметно жёстче.

Как достигаем:

- Пререндеренный HTML на CDN — контент виден до загрузки JS.
- Firebase Hosting: хешированные ассеты — `Cache-Control: max-age=31536000, immutable`,
  HTML — `no-cache`. Автоматический Brotli.
- Изображения: WebP (AVIF по возможности), явные `width`/`height` против сдвигов,
  `loading="lazy"` для всего ниже первого экрана, `fetchpriority="high"` +
  `preload` для изображения первого экрана.
- Шрифты: self-hosted woff2, кириллическое подмножество, preload, `swap`.
- Никаких тяжёлых зависимостей: анимации на CSS, иконки — только используемые,
  Firebase SDK — исключительно в чанке админки.
- Метрика грузится после того, как страница стала интерактивной.
- Проверка на реальном устройстве и в PageSpeed Insights перед сдачей.

## 11. Безопасность

- Правила Firestore и Storage по принципу «запрещено всё, кроме явно разрешённого».
- Публично читается только `published/current`; черновики недоступны анонимно.
- Custom claim `admin` вместо проверки по списку e-mail в коде.
- Ключи Firebase на клиенте не секретны — защиту обеспечивают правила, а не сокрытие
  конфига. Секреты (токен Telegram-бота, SMTP-пароль) живут только в переменных
  окружения функции.
- Ограничение частоты отправки формы, валидация на сервере, а не только в браузере.
- Заголовки безопасности через `firebase.json`: `X-Content-Type-Options`,
  `Referrer-Policy`, `Strict-Transport-Security`, аккуратный CSP (с учётом Метрики).
- `/admin` — `noindex`, запрет в `robots.txt`.

## 12. Инфраструктура и деплой

```
Firebase-проект
├── Hosting          статика + правила кеширования и заголовки

├── Authentication   один аккаунт администратора

└── Cloud Function   приём заявок, Telegram + e-mail
```

- Git-репозиторий (сейчас его нет — инициализируем на старте).
- Ветки: `main` — прод, `dev` — разработка.
- GitHub Actions: сборка и деплой на Firebase при пуше в `main`;
  превью-канал Firebase Hosting для пул-реквестов.
- Домен заказчика подключается к Firebase Hosting, SSL выпускается автоматически.
- Резервное копирование Firestore — по расписанию раз в неделю.
