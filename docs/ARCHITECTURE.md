# Как устроен проект

Документ объясняет принятые решения — то, что не видно из кода, но важно понимать
перед доработками.

---

## 1. Главный компромисс: статика против редактируемости

Требования тянут в разные стороны. Сайт рекламируется в Директе, значит нужна
максимальная скорость и хорошая индексация — это статика. Но заказчик должен менять
тексты и цены сам, без разработчика — это база данных и запросы из браузера.

Решение работает в три уровня.

**Уровень 1. Запекание при сборке.** Перед сборкой `scripts/fetch-content.mjs`
скачивает опубликованный контент и кладёт в `src/content/snapshot.json`. Пререндер
подставляет эти тексты прямо в HTML. Посетитель видит первый экран сразу, не дожидаясь
JavaScript; поисковый робот получает полноценную страницу с текстом и микроразметкой.

**Уровень 2. Обновление в браузере.** После гидратации `ContentProvider` в простое
запрашивает `content.json` из Storage. Если версия там новее запечённой, тексты
обновляются на лету. Правка в админке видна на сайте сразу после публикации.

**Уровень 3. Запасной вариант.** Если контент недоступен — нет сети, проект ещё не
настроен, из админки ни разу не публиковали — используется `src/content/default.ts`.
Сборка при этом не падает: деплой не должен зависеть от доступности стороннего сервиса.

Практическое следствие: цену, изменённую в админке, посетители видят немедленно,
а поисковики — после следующей пересборки. Для сайта, где контент меняется раз в
месяц, этого достаточно. Если понадобится мгновенно и для роботов — следующий шаг
описан в разделе 7.

## 2. Почему пререндер написан вручную

Изначально планировался `vite-react-ssg`. Он оказался несовместим с React Router 7:
внутри импортирует `react-router-dom/server.js`, которого в седьмой версии нет
(серверные API переехали в пакет `react-router`), а его peer-зависимость — React
Router 6.

Выбор был между откатом роутера на 6.x и собственным пререндером. Откат означал бы
переход на версию с четырнадцатью незакрытыми уязвимостями (XSS, open redirect,
отказ в обслуживании) — в 7.18 они исправлены. Поэтому написан свой пререндер:
`src/entry-server.tsx` плюс `scripts/prerender.mjs`, вместе около 80 строк. Он
использует штатные `createStaticHandler` и `createStaticRouter` из React Router и
не зависит от сторонней обвязки.

Побочный плюс — прозрачность: понятно, что и в какой момент попадает в HTML.

## 3. Управление содержимым `<head>`

Своё, в `src/lib/head.tsx`, вместо `react-helmet` и аналогов. Нужны ровно две вещи:
собрать теги в строку при пререндере и переписать их при переходах в браузере.
Библиотека решала бы ту же задачу, но добавила бы зависимость и лишний вес.

Теги помечаются атрибутом `data-head`, чтобы при смене страницы удалять только их и
не трогать то, что прописано в `index.html`.

## 4. Один документ вместо коллекций

Весь контент сайта — один документ Firestore `content/draft` (и `content/published`).
Объём — около 26 КБ при лимите документа в мегабайт, запас десятикратный.

Что это даёт: сохранение и публикация атомарны, поэтому сайт не может увидеть
наполовину обновлённый контент; загрузка админки — один запрос вместо десятка;
откат к прошлой версии — копирование одного документа.

Когда решение перестанет подходить: если появится блог с сотнями статей — тогда
статьи выносятся в отдельную коллекцию, а этот документ остаётся для страниц.

## 5. Схемы как источник правды

`src/schemas/content.ts` описывает контент на Zod. Из этих схем выводятся типы для
страниц, ими же проверяется контент при публикации и снапшот при сборке. Меняете поле
в схеме — TypeScript показывает все места, которые нужно поправить.

Публикация проверяет контент схемой и отказывается выкладывать то, что не проходит
проверку: испорченные данные не должны доезжать до сайта.

Про `.prefault({})` вместо `.default({})` у вложенных объектов: в Zod 4 `default`
принимает значение выходного типа, то есть требовал бы перечислить все поля целиком.
`prefault` подставляет значение до разбора и позволяет писать пустой объект.

## 6. Размер бандла и что где грузится

Firebase SDK весит больше, чем весь остальной сайт, поэтому он вынесен в отдельный
чанк и подключается динамическими импортами. Публичные страницы его не загружают
вовсе — контент они читают обычным `fetch` статического JSON.

Админка целиком за `React.lazy`: её код посетителям сайта не нужен.

Публичные страницы, наоборот, импортируются напрямую, без `lazy`. Причина
техническая: `renderToString` синхронный и не умеет ждать асинхронные компоненты.
Страниц шесть, они небольшие — выигрыш от разделения не оправдал бы усложнения.

Сейчас на главной: около 87 КБ (gzip) React с роутером, 52 КБ код страниц,
12 КБ работа с формой.

## 7. Что делать дальше, если понадобится

**Мгновенное обновление и для поисковиков.** Кнопка «Опубликовать» дёргает Cloud
Function, та отправляет `repository_dispatch` в GitHub Actions, экшен пересобирает и
деплоит сайт. Через 2–3 минуты свежий контент будет и в HTML. Требует тарифного плана
Blaze.

**Уведомления о заявках на Gmail.** Cloud Function `sendLeadEmail` при создании
документа в `leads` отправляет письмо через Gmail SMTP. Логин и пароль приложения
хранятся в Secret Manager, а не в коде. Настройка описана в
[GMAIL-SMTP.md](GMAIL-SMTP.md); требуется тариф Blaze.

**Калькулятор стоимости.** Три-четыре вопроса и вилка цены — заметно повышает
конверсию холодного трафика с РСЯ.

## 8. Безопасность

Ключи Firebase в коде сайта не секретны — так устроен этот сервис. Доступ ограничивают
правила `firestore.rules` и `storage.rules`, написанные по принципу «запрещено всё,
что не разрешено явно».

Права администратора выдаются через custom claim `admin`, а не списком почт в коде:
состав администраторов меняется без пересборки сайта.

Заявки: создавать может кто угодно (форма анонимна), читать — только администратор.
Правила дополнительно проверяют состав и длину полей и не пропускают заявку без
подтверждённого согласия на обработку данных.

Отдельная деталь для тех, кто будет править правила: слово `service` зарезервировано
языком Firestore Rules, поэтому поле заявки читается как `data['service']` — через
точку выражение не компилируется.

Антиспам в форме: скрытое поле-ловушка, проверка времени заполнения и ограничение
частоты отправок. Если пойдёт спам — подключается Yandex SmartCaptcha.

**Известная уязвимость в зависимостях.** `npm audit` показывает одну проблему высокой
критичности в react-router 7.18: обход CSRF в режиме RSC. Проект RSC не использует —
ни серверных экшенов, ни соответствующего роутера, — поэтому уязвимость неприменима.
Обновиться до исправленной версии, когда она выйдет; откатываться назад нельзя,
в ранних версиях уязвимостей больше.

## 9. Производительность

- HTML отдаётся готовым, стили и шрифты подгружаются заранее.
- Шрифты свои, а не Google Fonts: нет внешней зависимости и лишних 200–400 мс.
  Кириллица и латиница вынесены в отдельные файлы — на русской странице грузится
  только нужное.
- Изображения переводятся в WebP и сжимаются прямо в браузере при загрузке через
  админку. Проверено: фотография 3000×4000 весом 335 КБ превращается в 1350×1800
  весом 15 КБ. Без этого первая же загрузка фото с телефона обесценила бы всю
  работу над скоростью.
- Метрика подключается после того, как страница стала интерактивной, чтобы не
  портить LCP.
- Анимации появления — на CSS и `IntersectionObserver`, без библиотек. Полностью
  отключаются системной настройкой «уменьшить движение».
